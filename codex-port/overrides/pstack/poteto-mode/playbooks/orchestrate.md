Before work, read [the documentation policy](references/documentation-policy.md).

### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator chat: multi-day, many stacked PRs, dozens to hundreds of subagents, few human turns. One task driven to a predicate is Autonomous run. One ambitious run that needs a bespoke workflow is figure-it-out. Work that one agent could finish inside the session's budget is not a program.

Use the host's native subagent tools and read [Codex host guidance](references/host-delegation.md) before delegating. Keep the program's state in the existing local agent store, or outside the repository under `~/.codex/pstack/work/<task-slug>/`, per the documentation policy. Keep goals, worker ownership, current PR heads, verdicts, and pending decisions there. Put task-specific reasoning and verification summaries in the ticket or PR/MR body. Use native completion waits and available PR or CI event subscriptions. For a requested recurring monitor, use a Codex automation. Do not recreate the removed orchestration scripts, run polling loops, or relay status messages between workers.

#### Topology

- **One owner per PR.** The owner is the only writer of its branch and carries the PR from build through the authorized handoff or merge. Only the owner pushes, rebases, or retargets it. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call and within the user's authorization. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners.
- **A fresh worker for each independent task.** Its kickoff carries everything it needs, including each upstream report it depends on. Use native Codex subagents for task delegation. Give concurrent branch writers separate worktrees and explicit ownership, since local workers may share the filesystem. Keep checks that need this machine here, such as a `$pstack:control-ui` or `$pstack:control-cli` runtime check, local transcripts, a simulator, or local authentication. Pick each subagent's model and reasoning effort for the job per the Subagents section and host guidance.
- **A sub-coordinator only when one area has many parallel workers.** It owns that area's workers and kickoffs and sends you one rollup, never raw worker reports. Stop at three levels: you, sub-coordinators, and workers. Stay within the host's available concurrency slots, and start the next worker as each finishes instead of waiting on a whole batch.
- **Preserve built state when the next task needs it,** such as a checkout, uncommitted changes, or a running process. Follow the host guidance for handing off that state or following up with its owner. Message a worker only for a follow-up on the same work. Use native status and completion tools to check on it without starting another turn.
- **Each PR gets a verifier that isn't its author,** on a different model family. A verifier's pass at the current head is required before an authorized merge. Without merge authority, stop at the verified handoff.
- **Start with one unit.** Take it through kickoff, owner, verifier, and the authorized handoff or merge before you fan out, so a flaw in the kickoff costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

#### Supervision

- **Each kickoff names the evidence that proves the work is done,** such as a command and its expected output, a control-skill check, or an artifact. It also names the user's goal, the paths the worker may and may not write, and the actions it must not take. Give each worker the documentation policy's installed absolute path and require it to read the policy; include its text when that path is inaccessible. If you can't name the evidence, the unit isn't scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict. Read a sample of each sub-coordinator's kickoffs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** with the available forge tools or `gh pr view` and `gh pr checks` or their forge equivalents, not the worker's last report. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Judge it by its pushes and PR activity, not its status text. Retry by cause: a smaller scope after a context or memory limit, the same kickoff after a dropped connection, and a different model after a tool error. After two retries, drop the unit and replan around it. Stop the prior writer before handing its branch to a replacement. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Ask the user only for a real decision or a blocker,** such as an irreversible action, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.

**Reply:** what landed or reached verified handoff against the goal, each PR's live state and verdict with its link, what was dropped and why, the decisions waiting on the user, and the local state path for pickup.
